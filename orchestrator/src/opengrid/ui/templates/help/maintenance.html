Maintenance and operations

This section covers the base server's operational procedures: releases, database migrations, backups, the data lifecycle, firmware campaigns, calibration, charge schedules, a from-scratch bootstrap, logs, health checks and configuration files. The sources are deploy/RUNBOOK.md, deploy/README.md, the scripts under deploy/scripts/, the systemd units under deploy/systemd/, deploy/BOOTSTRAP.md, deploy/k8s/README.md, tests-perf/README.md and the r3.4.3 code. Where the documents disagree with the scripts or the code, this page follows the scripts and the code and says where they differ.

Every command runs as root on the base server unless it says otherwise. The server has no sudo. Never print secrets: /etc/opengrid/*.env, /root/opengrid-ui-credentials.txt and the Apache proxy-secret conf are read by scripts and are never cat-ed. Stop and start services by their exact unit name, never with pkill or killall by pattern, because test workspaces run as the same opengrid user as production.

Releases, deploy and rollback

A release is a directory that holds orchestrator/ and integration-sims/. deploy.sh copies it to /opt/opengrid/releases/<timestamp>, where the timestamp is YYYYMMDDHHMMSS. The symlink /opt/opengrid/current points at the live release, and every unit runs from /opt/opengrid/current. Releases are built from the git checkout /opt/opengrid/src, which belongs to user opengrid.

Tags and versions

The RUNBOOK builds a release from git archive HEAD of the server checkout after a fast-forward pull. The release directory is named after the short commit hash (/root/release-<rev>). deploy.sh takes any release directory, for example an extracted tagged checkout. It does not read or check a git tag. On the server a release is identified only by its timestamp directory, and /var/log/opengrid/deploy.log records which source directory went into which timestamp. This console release is r3.4.3: r3.4 plus the r3.4.1, r3.4.2 and r3.4.3 lanes.

Who may deploy

  • A deploy is run as root by whoever holds the root session on the base server. In BUILD.md terms that is the deploy role: "Only the deploy agent may run root scripts". The deploy role may touch only the og-* units, /etc/apache2/conf-available/opengrid*.conf, /etc/cron.d/opengrid, /etc/logrotate.d/opengrid, /opt/opengrid, /opt/ogsim and /var/lib/opengrid.
  • The console has no deploy button. No API route runs a deploy script.
  • Deploying while a FIRM or AS obligation is DELIVERING needs an explicit --during-delivery (see step 6 below). Use it only with the lead's agreement.

Deploy a release (RUNBOOK)

  1. Pick a quiet moment. Restarting og-engine, og-guardian or og-sim-* while a FIRM or AS obligation is DELIVERING interrupts it: hubs hold their last setpoint only for lease + hold, about 35 s. Prefer the minutes right after a Postgres checkpoint complete line, when the disk is quietest:
    grep 'checkpoint complete' /var/log/postgresql/postgresql-17-main.log | tail -1
  2. Update the server checkout:
    cd /opt/opengrid/src
    runuser -u opengrid -- env GIT_SSH_COMMAND="ssh -F /opt/opengrid/.ssh/config" git pull --ff-only
  3. Build the release directory:
    REV=$(runuser -u opengrid -- git rev-parse --short HEAD)
    rm -rf /root/release-$REV && mkdir /root/release-$REV
    runuser -u opengrid -- git archive HEAD | tar -x -C /root/release-$REV
  4. Install the release's own deploy.sh at its stable path, which survives across releases:
    install -m 755 /root/release-$REV/deploy/scripts/deploy.sh /opt/opengrid/deploy/scripts/deploy.sh
  5. Run the deploy:
    bash /opt/opengrid/deploy/scripts/deploy.sh /root/release-$REV
    Add --during-delivery as the first argument only when you have decided to interrupt a delivering obligation.
  6. Read the result. The script prints each step and appends it to /var/log/opengrid/deploy.log. Exit 0 ends with deploy OK: /opt/opengrid/releases/<timestamp>. Exit 3 means FIRM or AS obligations were delivering and nothing was changed. Exit 1 means a step failed and the script rolled back on its own.
  7. If the release changed integration-sims/config/fleet.yaml or scada.yaml, regenerate /etc/opengrid/sim/fleet.yaml and /etc/opengrid/sim/scada.yaml with the owner-approved zone blocks: python deploy/scripts/gen_sim_overrides.py --release <release_dir> --out /etc/opengrid/sim --zones LZ_AEN (add LZ_LCRA,LZ_RAYBN when those blocks are enabled in production; they are regulated and unavailable under D-37; --dry-run first). The script enables exactly the listed zones. Otherwise the sims keep running the old topology (see Bootstrap). Regenerate before the deploy: the seed reads the same file.
  8. If the release changed the operator accounts or deploy/apache/opengrid.conf, install the conf, then run apache2ctl configtest && systemctl reload apache2. Never reload a config that fails configtest.

Verification after a deploy

  1. All units are active:
    for u in og-engine og-guardian og-safestop og-api og-feeds og-settle og-sim-fleet og-sim-scada og-sim-market og-sim-control og-sim-utility; do printf '%s=%s ' "$u" "$(systemctl is-active "$u")"; done; echo
    (og-sim-utility needs /etc/opengrid/utility_sim.env; see the warning below.)
  2. The API answers on loopback: curl -fsS http://localhost:8080/og/api/health >/dev/null && echo api-ok
  3. https://base.tocy-net.net/og/ loads for both an operator and a viewer.
  4. Guardian verdicts are mostly PASS (Dispatch and Health screens).
  5. og.invariant_check shows 0 new violations.
  6. Engine cycle p99 is in range: curl -s http://localhost:9101/metrics | grep og_engine_cycle_latency_ms. The guardian and safe-stop MQTT sessions are connected: curl -s http://localhost:9103/metrics | grep og_mqtt_connected and the same on port 9106.
  7. No new errors: journalctl -u og-engine -u og-guardian -u og-settle -u og-api --since -10min -o cat | grep -E '"ERROR"|Traceback'
  8. Optionally run the smoke test (see Health checks).

Rollback

  1. List the releases, newest first: ls -1t /opt/opengrid/releases
  2. Roll back to one of them by its timestamp name: bash /opt/opengrid/deploy/scripts/rollback.sh <release_timestamp>
  3. rollback.sh re-points current, restarts both targets and polls /og/api/health the same way deploy.sh does. It prints rollback OK. If the health check fails it prints rollback health check FAILED - manual intervention needed and exits 1.
  4. Verify as after a deploy.

A rollback never runs migrations and never touches the database. Older code runs against the newer schema because migrations are additive. Data-only migrations such as 0022_demo_as_ecrs.sql are not reverted, so reverse them by hand if needed. If a bad migration has to be undone, restore from a backup (see Backups).

See also the playbook Release.

All additive. See Migrations added in r3.4.1 to r3.4.3.
Numbering
A four-digit, zero-padded prefix, an underscore and a short snake_case description. The runner accepts any file matching ^(\d+)_.*\.sql$ and applies files in sorted filename order. A new migration takes the next free number.
Runner
python -m opengrid.platform.db migrate (opengrid.platform.db.migrate_sync). It creates og.schema_migrations(filename, applied_at) if the table is missing, skips every file already recorded there, and runs each pending file in its own transaction, recording its filename in the same transaction.
Lock safety
The runner migrates while the previous release is still writing telemetry every few seconds. Each session sets lock_timeout = '5s' and statement_timeout = '15min'. A file that hits the lock timeout is rolled back and retried up to 3 more times, with backoff of 2, 4 and 8 s. After that it raises MigrationLockTimeoutError, nothing of that file is applied, and deploy.sh rolls back the code.
Additive-only rule
Migrations are forward-only. Each one adds columns, tables, functions or constraints, and never renames or drops in the same migration. That way a rollback to older code tolerates a schema that is slightly ahead of it. Migrations are written to be idempotent (IF NOT EXISTS, ON CONFLICT DO NOTHING), and a widened CHECK is added NOT VALID so that it does not scan. Dropping an index that older code does not need is allowed (0042, DROP INDEX IF EXISTS under lock_timeout). There are no down-migrations.
Credentials
The DSN is built from [postgres] in the config, with the password taken from the environment variable OG_DB_PASSWORD (loaded from secrets.env). The runner fails loudly if that variable is unset. OG_DB_USER and OG_DB_PORT can override the user and the port.

Run migrations by hand

Normally deploy.sh runs them. To run them by hand against the live release, use the same pattern as deploy.sh. It sources the env files without printing them:

  1. runuser -u opengrid -- bash -c 'set -a; . /etc/opengrid/secrets.env; . /etc/opengrid/api_keys.env; set +a; export OG_CONFIG=/opt/opengrid/current/orchestrator/config/orchestrator.toml PYTHONPATH=/opt/opengrid/current/orchestrator/src; exec /opt/opengrid/venv/bin/python -m opengrid.platform.db migrate'
  2. The output is Applied N migration(s): ... or No pending migrations.

create_schema.sh and the schema snapshot (r3.4.1)

deploy/scripts/create_schema.sh creates the database from nothing and is idempotent: the role (password generated into secrets.env when absent and passed to psql over stdin, never in argv), the database, any extensions (none are required; PostgreSQL 13 or later for gen_random_uuid()), schema og, then every migration through the same runner. It is phases c and d of bootstrap_from_scratch.sh and the migrate Job of the Kubernetes installer.

Options
--release, --etc, --db-port/--db-name/--db-role, --db-host, --config, --fresh-db (refused on port 5432), --no-migrate, --snapshot FILE, --check-snapshot, --dry-run. With OG_PG_ADMIN_PASSWORD in the environment it connects over TCP as OG_PG_ADMIN_USER (default postgres) instead of the local socket.
Snapshot
orchestrator/schema/og_schema.sql is the normalised pg_dump --schema-only of schema og on a fresh database after all migrations (no owners, privileges or version banner). make schema-check rebuilds a fresh og_t_schema on the test cluster (5433) and exits 3 on any difference; make schema-snapshot regenerates the file, which is committed with the migration that changed it.

During the r3.4.3 assembly the committed snapshot was regenerated through 0050_delivery_record.sql. The migrations merged after it (0051, 0053, 0054) change the schema, so unless the snapshot was regenerated again, make schema-check reports drift (exit 3) and a --fresh-db bootstrap prints "WARN: the fresh schema differs" in phase d and continues. Regenerate it with make schema-snapshot on the test cluster.

Restore test and restore (RUNBOOK)

The restore path is covered by tests/integration/platform/test_es01_s05_restore_and_verify.py. That test dumps the database, restores it into a second database and checks that the trace hash chain still verifies. Always restore into a scratch database first.

  1. Create the scratch database: runuser -u postgres -- createdb -O opengrid og_restore_check
  2. Restore into it:
    runuser -u opengrid -- bash -lc 'set -a; . /etc/opengrid/secrets.env; set +a; export PGPASSWORD="$OG_DB_PASSWORD"; pg_restore -h localhost -U opengrid -d og_restore_check --no-owner /srv/ogbackup/og-YYYY-MM-DD.dump'
  3. Check og_restore_check: compare row counts and run the trace verify against it.
  4. To replace production (this needs downtime), stop the application: systemctl stop ogsim.target opengrid.target
  5. runuser -u postgres -- psql -c "ALTER DATABASE og RENAME TO og_before_restore"
  6. runuser -u postgres -- psql -c "ALTER DATABASE og_restore_check RENAME TO og"
  7. systemctl start opengrid.target ogsim.target, then verify as after a deploy.
  8. Keep og_before_restore until the restored system has been verified. Drop it only after that, and only with the lead's agreement.

deploy/README.md still describes a restore that runs dropdb og in place and reads from /var/lib/opengrid/backups. Use the RUNBOOK procedure above. The backup script writes to /srv/ogbackup.

  • Only tables in the code whitelist opengrid.lifecycle.policy.DELETABLE_TABLES are ever deleted from, whatever their policy row says.
  • A day is dropped once its end is at or before today 00:00 UTC minus keep_days. All days are UTC days.
  • Unarchived data is never dropped. A PARTITION drop detaches the partition, recounts the rows per day, re-exports a day whose count changed, re-verifies every export from disk and only then drops it. Any failure re-attaches the partition. A DELETE-mode day is exported and verified first, then deleted in batches of [lifecycle].batch_rows (at most 10,000).

Cold archive

  • Path: /srv/ogbackup/cold/<archive>/<yyyy>/<mm>/<dd>.csv.gz plus <dd>.manifest.json. The format is zstd (.csv.zst) when the zstandard package is installed. The server venv does not have it, so files are gzip.
  • Files are written once. The job writes to .partial, fsyncs, renames and sets mode 0440. It records the SHA-256 and size in the manifest and in og.lifecycle_archive, and re-reads the file before any drop. A day that later gains rows gets a new revision file (<dd>.r2.csv.gz).
  • Billing: /srv/ogbackup/cold/billing/<yyyy>/<mm>/ holds invoice_line.csv.gz, pnl.csv.gz and manifest.json. Each month is written once, a day after it closes. The manifest carries a checksum digest; there is no cryptographic signature.
  • An export refuses to start when the cold volume has less than [lifecycle].cold_min_free_gb free (default 5). No export means no drop. The cold tier has no pruning of its own.

Rollups

telemetry_1m and telemetry_15m hold one row per hub per bucket (p_kw_avg/min/max, soc_kwh_last, energy_in_kwh, energy_out_kwh, sample_count). Each rollup keeps a watermark in og.lifecycle_watermark. Every run re-aggregates from the watermark minus rollup_late_minutes (default 15), and at most rollup_max_hours_per_run (default 6 h) per run. The 15-minute buckets are built from the 1-minute rows. Re-running any range is idempotent.

Changing retention

  • Table retention: UPDATE og.data_retention SET keep_days = ... WHERE table_name = '...' (or hot_days, archive). It takes effect on the next hourly run. Lowering keep_days drops more data after it has been exported.
  • Legal hold: UPDATE og.data_retention SET legal_hold = true WHERE table_name = '...' stops every deletion for that table. Exports still run.
  • Trace retention per event class lives in og.retention_policy. Read it with GET /og/api/retention (viewer) and change it with PUT /og/api/retention (operator, body event_class, retention_days). Each change is traced as OPERATOR_ACTION / CONFIG_CHANGE.
  • At the 2 s simulator cadence, 7 days of raw telemetry does not fit the 147 GB /srv/pgdata. The design document recommends keep_days = 3 for telemetry and 14 for grant, command_batch and command_ack until the cadence is 10 s. The r3.4 config sets hub telemetry to 10 s ([fleet].telemetry_interval_s; [health] comment, V-32).

Firmware campaigns

Code: orchestrator/src/opengrid/firmware/. Guardian check G-36. API: /og/api/firmware/*. Schema: migration 0037_firmware_campaign.sql. Operator note: docs/orchestrator/07-delivery/16-firmware-updates.md.

At r3.4.3 firmware campaigns are API only. The Firmware update card on the Fleet page is still a disabled placeholder ("available after R3.1"), even though the API is mounted. The catalogue in orchestrator.toml is a demo catalogue (1.20.0 for RevA to RevD) with placeholder hashes for the simulated fleet.

Rules

  • Only catalogued images can be targeted. A catalogue entry is a version and hardware revision with its sha256 ([[firmware.catalogue]], GET /og/api/firmware/catalogue). Hubs without a matching entry, or already on the version, are listed as SKIPPED.
  • A downgrade needs allow_downgrade and always needs a second operator.
  • The console never sends anything to a battery. The engine asks, and the guardian re-checks each hub (G-36) and signs one command per attempt with a fresh (epoch, seq) and a 120 s lease.

Staged rollout

  1. Propose: POST /og/api/firmware/campaigns with name, target_version, selection (hub_ids, bank_ids, zones, feeder_ids, hardware_revisions, firmware_versions) and reason. Optional fields: waves (default canary 1 hub, then size_pct 25), bank_max_concurrent_pct and feeder_max_concurrent_pct (default 10 each, minimum 1 hub), max_failures (default 2) and max_failure_pct (default 5), window_start and window_end, allow_downgrade, override_committed. The hub list is fixed at this moment.
  2. Confirm within 60 s: POST /og/api/firmware/campaigns/{campaign_id}/confirm. An expired proposal is aborted, so propose again.
  3. Second operator, when the proposal shows requires_second_operator: more than 50 hubs, override_committed on a hub serving a COMMITTED or DELIVERING obligation, or a downgrade. A different operator calls POST .../{campaign_id}/approve. The proposer and the confirmer cannot approve.
  4. The engine starts the campaign on its next cycle. A wave starts only when every hub of the previous wave has finished. A canary wave with no success halts the campaign.

G-36 refuses to sign unless all of these hold: the campaign is RUNNING; the hub is online, not inside a safe stop and not already updating; the hub serves no committed obligation in the next 15 minutes (unless overridden by two operators); SoC is at least reserve + 10 % of capacity; the image and its sha256 are catalogued for the hub's hardware; and the bank and feeder caps hold. A refusal is a hold, not a failure, and the hub is re-checked 60 s later. Catalogue refusals are terminal.

Watching

  • GET /og/api/firmware/campaigns and GET .../{campaign_id} show campaign state (PROPOSED, APPROVED, RUNNING, PAUSED, HALTED, COMPLETED, ABORTED) and per-hub state (PENDING, SENT, UPDATING, SUCCEEDED, FAILED, ROLLED_BACK, SKIPPED).
  • GET .../{campaign_id}/events?after=<event_id> is the feed of every transition, including the hub's own progress (HUB_DOWNLOADING to HUB_DONE or HUB_FAILED).
  • Alerts: ALR-FIRMWARE-CAMPAIGN-STARTED and ALR-FIRMWARE-CAMPAIGN-COMPLETED (info), ALR-FIRMWARE-HUB-FAILED (warning) and ALR-FIRMWARE-CAMPAIGN-HALTED (critical). See alert rules.

Halt, retry, rollback

Situation or actionHowBehaviour
Transient failureautomaticNo ack before the lease expired, the hub quiet for 10 minutes while updating, or a download or verify error. Retried up to 3 attempts with backoff 60 s, 120 s, 240 s and so on, capped at 15 minutes. Each retry is re-checked and re-signed.
Terminal failureautomaticA sha256 mismatch, a hardware incompatibility, a bad signature, or an install or boot failure (the battery reverts by itself). Not retried, and alerted. Only terminal failures count toward the halt threshold.
HaltautomaticAt max_failures terminal failures or max_failure_pct of the campaign, whichever comes first. The campaign becomes HALTED and never resumes directly.
Pause / resumePOST .../{campaign_id}/pause, .../resumeHubs already updating finish, and nothing new starts.
AbortPOST .../{campaign_id}/abortPending hubs become SKIPPED. A hub that is mid-install cannot be recalled.
Retry failed hubsPOST .../{campaign_id}/retry-failed, then .../retry-failed/{proposal_id}/confirmGives the hubs a fresh attempt budget. A HALTED campaign becomes PAUSED, and you then resume it deliberately.
Roll back one hubPOST .../{campaign_id}/hubs/{hub_id}/rollback, then .../rollback/{proposal_id}/confirmInstalls the version the hub ran before the campaign. Allowed while the campaign is paused, halted or completed.

Before retrying a halted campaign, read the failures and compare the failed hubs' cohort with the control cohort (RB-005). Roll back the affected hubs if the image is suspect. See the playbook Firmware.

Calibration and asset health

Code: orchestrator/src/opengrid/assets/. Schema: migrations 0011_asset_health.sql and 0016_calibration_command.sql. Each hub inverter has an asset state in og.hub_inverter_pq.asset_state:

OK → WATCH → DEGRADED / DERATED → QUARANTINED → AWAITING_REPLACEMENT → RECOMMISSIONING → OK

The calibration loop

  1. Request. The request comes either from the automatic drift sweep (a WATCH hub) or from an operator on the PQ screen: Request calibration (step 1 of 2), then confirm. The API equivalent is POST /og/api/hubs/{hub_id}/calibrate, then .../calibrate/{proposal_id}/confirm. The confirm writes a PENDING row in og.calibration_attempt, with a correction equal to the negative of the latest measured offset, clipped to firmware bounds. It returns 409 when the ladder refuses: a live PQ-sensitive delivery on the hub, the per-hub 24 h rate limit, or no fresh drift measurement.
  2. Sign. og-guardian polls pending attempts, runs G-25 and, on PASS, signs and publishes the command to <root>/cmd/cal/<hub_id> (QoS 1). On refusal the row stays pending. The API never signs.
  3. Ack. The hub answers on ack/cal/<hub_id>. og-engine routes that ack to opengrid.assets.calibration_ack.handle_calibration_ack, which classifies the outcome as CORRECTED, IMPROVED, NO_CHANGE or WORSE_ROLLED_BACK and advances the asset state.
  4. Escalate. NO_CHANGE, WORSE_ROLLED_BACK, or a REJECTED or EXPIRED ack opens a maintenance work order in og.maintenance_work_order. A physical inverter swap is recorded, never decided, here. Substitution of delivery is the allocator's job.

Charge schedules (D-30)

Owner grid-charging windows limit when hubs may charge from the grid. Solar charging is always allowed. The windows are stored in og.owner_charge_window (migration 0038_owner_charge_window.sql) and resolved by opengrid.core.charge_windows. The selector and the API share that one resolver, so they always agree.

Format
"HH:MM-HH:MM" in America/Chicago local time, 24 h, end exclusive. A window may wrap midnight (22:00-06:00). A scope takes at most 4 windows, with no duplicates and no zero-length windows. Overlaps are allowed, and their union applies. An empty list is a valid override that means no grid charging at that scope.
Scopes
From least to most specific: FLEET < PROVIDER < ZONE < SUBSTATION < FEEDER < BANK < HUB. The most specific scope that has a row wins. FLEET uses scope_ref * and cannot be removed, only edited. PROVIDER is the zone's regulated utility (for example AUSTIN_ENERGY) or, in a competitive zone, its TDSP (for example ONCOR), resolved from tdsp_tariffs.toml.
Default
Migration 0038 seeds FLEET * = ["22:00-06:00"]. [selector.owner_charge_windows] in orchestrator.toml (for example AUSTIN_ENERGY) is a fallback. Database rows win over it, and it wins over the built-in default.

Change windows in the UI (Fleet page, Charging schedule)

  1. Open /og/fleet and go to the Charging schedule panel. Viewers see the current windows grouped by scope. Operators also see Set windows for a scope.
  2. Pick the Scope, enter the Scope id (the Fleet default applies to every hub without an override), set up to 4 windows (Add window), and give a Reason.
  3. Click Review change (step 1 of 2), read the old and new windows, then confirm to save.
  4. To drop an override, click Remove on its row, then confirm. The next less specific scope then applies.
  5. Check the result with Preview effective schedule for hub, which shows the effective windows and the scope they come from.

A11 injects an anomaly through the simulator control plane (loopback port 8091), which raises a real alert on the production console. Acknowledge that alert after the run, and do not run the smoke test while a FIRM or AS obligation is delivering.

Configuration files

This page names configuration files and sections only. It never shows values from /etc/opengrid. The main TOML configuration is not under /etc/opengrid. It ships inside each release, and every unit points at it with OG_CONFIG=/opt/opengrid/current/orchestrator/config/orchestrator.toml, so a config change is a code change that is deployed like any release.
