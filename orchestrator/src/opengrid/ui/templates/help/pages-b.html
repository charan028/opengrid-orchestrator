Markets & feeds (/og/markets)

What the market and weather inputs look like right now, what price the optimizer plans against, how many market opportunities the optimizer selected and committed (a simulated funnel: nothing is sent to ERCOT), and whether each feed is live. Every panel is read-only. The screen re-renders itself on the server every 30 seconds (an htmx poll of its own URL, not a live stream: market data does not need the 2-second cadence), so the header badge reads poll: 30s.

What the operator can do

Nothing on this screen writes. Viewer and operator see the same page. Act on what you see elsewhere: a stale or breaker-open feed raises ALR-FEED-STALE or ALR-FEED-LGV-EXHAUSTED (see Alert rules) on System Health; a feed stale past its threshold puts the platform into the NO_NEW_COMMITMENTS degraded mode (Degraded modes).

The forecast band shows one zone only (LZ_NORTH). The optimizer forecasts every load zone; the others are not drawn at r3.4.3.

Related playbooks: Price spike, AS deployment, Normal day, Broker or database outage.

System Health (/og/health)

Whether the platform itself is working: process heartbeats, feed freshness, hub connectivity, the control-cycle latency and the open alerts. First paint comes from GET /og/api/health; after that the page subscribes to the server-sent event stream /og/api/stream/health, which re-sends the whole health payload about every 2 seconds. The header badge reads live, or reconnecting while the stream is down.

Profitability (/og/profitability)

Was the optimizer worth it? Settled revenue minus energy, degradation and penalties, per interval, next to what a simple rule would have earned, plus the value the commitment lock deliberately gave up and the economics per kW. Rows come from the same settlement view as Billing & audit, so a contract carries the same label on both screens. The page re-renders itself every 30 seconds (poll: 30s). All amounts are USD; intervals and days are in Central time (America/Chicago).

Filters

Customer, Contract, Service (HOME, ERCOT_ENERGY, ERCOT_AS, DIST_DEFERRAL, PARTNER_CAPACITY, DATA_CENTER) and Day, applied with Filter. A filter is a URL query parameter, so a filtered view can be bookmarked. Filters apply to the totals, the Net by contract and Net by day tables, the per-interval table and the MILP vs rule baseline chart; the MILP value-added panel, the per-kW panel and its capacity split line are not filtered. The Service list has no REGULATED_CAPACITY entry at r3.4.3, so tolling (D-29) rows cannot be isolated by service; filter by their Contract instead.

Billing & audit (/og/billing)

What each buyer is billed, the measurement behind it, and a tamper-evident record of every decision that led there. The page is rendered on demand (no poll). Invoice lines come from the shared settlement view (same labels as Profitability); M&V performance and the trace explorer have their own endpoints.

Filters

The header filter has Trace class (free text, e.g. a decision or event class), From and To (date and time), applied with Filter. From/To set the invoice period (blank means the last 30 days through tomorrow) and the trace window. The invoice filter under the heading has Customer and Contract. Clicking an obligation shows only its lines; Showing one obligation clears that.

Trace chain verify in practice

  1. Open /og/billing and press Run chain verify.
  2. PASS with N streams: the audit record is intact. Nothing else to do.
  3. FAIL: note the stream id, sequence and reason in the result. Do not edit or delete trace rows. The periodic check raises ALR-TRACE-VERIFY-FAILED (Alert rules); treat it as a security incident and follow Security. The journal itself is described under Trace journal.
  4. A FAIL with an error message and 0 streams means the API could not be reached, not that the chain is broken. Retry once the API is back.

Power quality & assets (/og/pq)

Inverters that drifted, failed a calibration or were quarantined, the work orders raised for them, and for one hub its measured waveform, harmonics, bank measurement, asset history and calibration history. The screen computes no power-quality figure itself; everything comes from the PQ API. A missing measurement is never shown as compliant (K1). Rendered on demand.

Choosing a hub

Type a hub id in Hub and press Show, or click a hub in the work-order table. With no hub given, the first hub with an OPEN work order is shown. An unknown hub shows "No hub ... (or it has no power-quality record)".

Scenarios (/ogsim/)

Scenarios in the Tools part of the left menu opens the integration-sims control plane, ogsim.control. It is a separate application (service og-sim-control, listening on localhost port 8091) that Apache publishes at /ogsim/ with its own Basic Auth sign-in, separate from the console's. It is the single place to inject anomalies into the market, fleet, SCADA and customer simulators: by hand, from a scripted scenario, or randomly. It has no access to the orchestrator's database and changes nothing in OpenGrid directly; the orchestrator only sees the effects (a price spike in a feed, an overloaded bank, a silent hub). Its header has a small Help link back to this section.

Use it only on test and demonstration systems. Everything injected here looks real to the orchestrator: alerts open, the guardian vetoes, holds and safe stops can follow.

How an injection reaches the simulators

Each anomaly type has one owning simulator. Market types (including the ERCOT AS instruction types) go to the market simulator's admin HTTP API; all other types (fleet, SCADA, customer, utility) are published over MQTT on the scenario command topic for the owning simulator to execute. Utility types are executed by ogsim.utility_aen (service og-sim-utility, r3.4.3, installed by r343_utility_sim_install.sh, dry run by default), which speaks for AUSTIN_ENERGY over one of its channels: the utility customer API or, when enabled, the DNP3 grid link (see utility API, grid link). It reads measured delivery (delivery_state, D-38) back from the call status. LCRA and RAYBURN are disabled in the sim (regulated, no contract). The customer simulator (og-sim-customer) is installed but not enabled until the customer services go live, so customer types have no effect until then. Manual, scenario and random injections share one registry, so the random engine's max_concurrent cap (5 by default) counts all of them; an arrival over the cap is dropped, not queued.

Random mode

Configured in integration-sims/config/random.yaml (or OGSIM_CONFIG_DIR). Each enabled type fires as an independent Poisson process at rate_per_hour, scaled by the profile; duration and numeric parameters are drawn uniformly from configured ranges. One seeded generator (seed) makes a run reproducible.
