Integrations

Every MQTT topic below lives under the configured root [mqtt].topic_root (production og/v1), written <root>. The full topic table with QoS and schemas is in MQTT topics.

ERCOT public API feeds

og-feeds polls the ERCOT public reports API ([feeds.ercot].base_url) with a subscription key and an ERCOT API account. The key and the account are read from environment variables named in the config (subscription_key_env, subscription_key_secondary_env, username_env, password_env). Their values live in the environment files under /etc/opengrid. All requests share one token bucket (budget_requests_per_min = 24), and each source has one circuit breaker.

At r3.4.3 the scheduler polls exactly the products listed in [feeds.ercot].products. A product that is not listed is never polled, whatever its own switch says. An unknown product id in the list stops og-feeds at start-up with a configuration error. When the key is absent from the file, every known product is polled. A failed or skipped poll is retried with a capped exponential backoff from 5 minutes up to 60 minutes, and never later than the product's normal cadence.

Price extremes are kept and flagged (FR-ING-117, since r3.4.1)

An extreme value is corroborated when the same series' previous 15-minute interval carried the same value to the cent. The check runs within the batch and against the row already stored from an earlier posting. Both rows are then written as GOOD, and a later re-posting never demotes a corroborated row. Other corroborators (system lambda near its cap, shadow prices) are not ingested, so a one-interval spike stays flagged. While a series' latest price is EXTREME_UNCORROBORATED, the forecast marks its slots NOT_FOR_FIRM and nothing firm is declared from it.

EIA and NWS

EIA v2 ([feeds.eia])
Hourly demand (type=D) for respondent ERCO from /electricity/rto/region-data/data/. The API key is read from the environment variable named by api_key_env (EIA_API_KEY). EIA is polled only from inside the ERCOT np6-345-cd poll, when that product's breaker blocks the request, so it is idle while ERCOT is healthy. An old EIA row raises ALR-FEED-STALE only when the ERCOT product it backs is itself unavailable. Staleness eia_fresh_s 10800. Stored in og.feed_obs.
NWS ([feeds.nws])
api.weather.gov, no key; a descriptive User-Agent is sent. The grid point (grid_point) is resolved once at start-up. After that the hourly forecast is polled every hour with If-Modified-Since. Staleness nws_fresh_s 10800. Stored in og.feed_obs and used by the forecast. Not firm-blocking.

ERCOT AS deployment instructions (D-35, since r3.4.2)

og-feeds polls ERCOT's ancillary-service dispatch instructions (DEPLOY_AS and RECALL_AS for ECRS, RRS, Reg-Up/Down and Non-Spin). The poll runs every 5 s, first in each tick and independent of the public-feed polls. The source is the ercot_mms adapter (EWS get VDIs, acknowledged with change VDIs), built from [feeds.ercot_as_poll.mms]. Until go-live the endpoint is the ogsim MMS simulator on the market sim (localhost port 8090, path /mms/ews/). A real MMS endpoint replaces it by configuration only. Nothing is ever submitted to ERCOT. Configuration, refusals and alerts are in AS poll: configuration and refusals.

Which award
An instruction names an ERCOT resource and an AS type. [feeds.ercot_as_poll.awards] maps "<resource>:<AS type>" to the ERCOT_AS contract. The obligation of that contract whose window covers the instruction's start is the one deployed.
Same rules as the operator
Each instruction goes through the same core call function (opengrid.calls) as POST /og/api/dispatch/as-deployments, with origin ERCOT_POLL. It deploys only ERCOT_AS awards, never the utility TOLLING contract. A recall ends the deployment it names. Each accepted instruction writes an og.as_deployment row (source ERCOT) and an og.dispatch_call row.
Idempotent and ordered
The instruction id is the idempotency key, so a duplicate delivery never deploys twice and gets the same answer. Each batch is processed in issue order. A recall that arrives before its deployment is held, and the deployment is then never started.
Trace and answer
Every decision is traced on stream ercot_as_poll (origin ERCOT_POLL) before ERCOT is answered. The answer is ACCEPT, or REJECT with <status> <reason code>.
Settlement
From r3.4.3, og-settle prices ERCOT_AS capacity at the cleared DAM MCPC (np4-188-cd) of the award's product for the delivery hour (price flag MCPC). Without an MCPC observation it falls back to the opportunity's own figure (flag OPPORTUNITY_PRICE, logged). The settlement trace records price_per_kwh and price_flag.
Simulating ERCOT
On the /ogsim/ control page, run scenarios ercot_as_01_ecrs_deploy to ercot_as_07_exceed_award or single ercot_as_* injections. The scenarios cover a normal ECRS deployment, an RRS event, a recall with out-of-order delivery, a duplicate, a malformed instruction, an unknown award and a deployment over the award. The simulator adds 1-4 s delivery jitter, occasional duplicates and out-of-order batches, and lists every instruction with our answer at /mms/admin/vdis. The ercot_as_* entries in the random-event catalogue ship disabled (rate 0).

A refused instruction is traced, answered REJECT with <status> <reason code>, and raises ALR-ERCOT-AS-REFUSED (warning). Nothing is deployed. The poller's own reason codes come first; everything else is the core call function's own reason code and HTTP status.

Battery telemetry, acks and DEVICE-INFO

Telemetry <root>/tel/<zone>/<bank_id>/<hub_id>
QoS 0, every 10 s per hub ([fleet].telemetry_interval_s). og-engine's ingest loop updates the fleet twin and writes og.hub_state and og.telemetry (kept 14 days). og-guardian subscribes separately for its own hub-state read. A hub is stale after 25 s ([health].hub_stale_s) and offline after 60 s (hub_offline_s). These two values are used everywhere (health, fleet twin, screens). A missed sample is covered by the next one. Since r3.4.3, og-settle also reads telemetry to measure delivery of discharge calls (delivery verification).
Acks <root>/ack/<hub_id>
QoS 1, one per received command batch. Stored in og.command_ack and read by og-engine and og-guardian.
DEVICE-INFO <root>/hub/<hub_id>/info
QoS 1, retained. The topic is set by [mqtt].device_info_topic (default hub/+/info); schema device_info.schema.json. og-engine handles it through opengrid.fleet.device_info. The hub is taken from the topic: a payload whose hub_id differs, or an unknown hub, is rejected and traced, and nothing is written. Reported units, rated kW and kWh, reserve floor and latitude/longitude go only to the og.hub.device_* columns (migration 0043). A report never changes the seed columns the fleet plans and signs with (units, p_kw, e_kwh, r_kwh, lat, lon). A difference raises ALR-DEVICE-RATING-MISMATCH. Every report is traced as DEVICE_INFO or DEVICE_INFO_REJECTED on stream fleet_device_info. Since r3.4.2, G-35 and the selector use a truck's reported position while it is fresher than 300 s.

Firmware status (ack/fw)

<root>/ack/fw/<hub_id>, QoS 1, schema firmware_status.schema.json. The hub reports each phase of an update (for example DOWNLOADING, INSTALLING, REBOOTING) with a timestamp. og-engine validates it with its own parser (never the command-ack parser) and hands it to opengrid.firmware.ingest. That module updates og.firmware_job and appends og.firmware_job_event. The executor then retries transient failures with backoff, raises ALR-FIRMWARE-HUB-FAILED on a terminal one, and halts or completes the campaign. After a successful update the hub republishes DEVICE-INFO with the new firmware version. Since r3.4.3, guardian G-19 counts hubs with an update in flight as unavailable. See firmware maintenance and the firmware playbook.

Utility SCADA and protocol adapters

The only SCADA ingest path running at r3.4.3 is MQTT. It uses two topics: <root>/scada/<bank_id> for bank signals (QoS 0) and <root>/scada/instruction/<bank_id> for utility ESTOP / BLOCK / LIMIT instructions (QoS 1). Today the simulator ogsim.scada publishes both. og-engine stores readings in og.feed_obs (source scada) for the DIST_DEFERRAL PI loop and guardian G-03. og-guardian subscribes to instructions itself (G-15, K5). Health watches freshness (ALR-SCADA-SILENT, ALR-SCADA-SILENT-BANK, DIST_DEFERRAL_OPEN_LOOP). Since r3.4.3, delivery verification compares SCADA REAL_POWER_KW with battery telemetry on metered banks (ALR-DELIVERY-METER-MISMATCH).

opengrid.integrations holds production protocol backends behind one ScadaSource interface (docs docs/orchestrator/07-delivery/integrations/protocol-adapters.md). They emit the same ScadaBankSignal / ScadaUtilityInstruction models. In production they republish on the same MQTT topics through MqttBridgeSink, so the guardian keeps its independent subscription.

Utility grid-control link (D-34, disabled)

The grid link lets a utility's control system (EMS), with Austin Energy first, control OpenGrid directly. It shipped in r3.4.1; the spec is docs/orchestrator/07-delivery/integrations/grid-link.md. The EMS sends D-29 toll calls (discharge only, at most 90 minutes) and the existing L2 LIMIT and BLOCK, per bank or zone. It reads back available and delivered kW, the call state, SoC (for the utility and per bank) and alarms. OpenGrid is the DNP3 outstation (IEEE 1815, point layout opengrid-gridlink-v1, in-house codec, no extra package) and the EMS is the master, over mutual TLS. Real Texas EMS links are usually ICCP. The link's service is protocol-neutral, so an ICCP transport can be added later with a licensed TASE.2 stack.

Disabled by default. og-engine starts the link at startup (opengrid.integrations.grid_link.runner.start_grid_link, called from the engine main) only when [grid_link].enabled and at least one utility entry's enabled are both true; otherwise nothing listens on the link port. A link failure is logged ("grid link task stopped") and never stops the engine. grid_link_enable_loopback.sh --apply turns it on for AUSTIN_ENERGY on localhost port 20001 only and waits for that port. No real utility EMS has connected.

Toll calls
The EMS stages setpoint kW, duration and its own call id on analog outputs 0–2, then operates CALL_EXECUTE (CROB 0, select-before-operate). The call goes through the same core call function (opengrid.calls) as the Dispatch screen's utility call and the utility customer API. Its origin is GRID_LINK, and the EMS call id is the idempotency key. The core checks the tolling obligation and the 90-minute cap. It then writes the deployment, the call ledger (og.dispatch_call), the trace and the operator alert (ALR-UTILITY-CALL / ALR-UTILITY-CALL-REFUSED). CALL_CANCEL is CROB 1. The outcome shows on the CALL_STATE and CALL_REASON points. From r3.4.3 the core reports measured delivery: RAMPING and DELIVERING both show as ACTIVE on the link.
Delivered kW
DELIVERED_KW (AI 1) and the per-bank delivered points come from the fleet twin's telemetry. CALL_DELIVERED_KW (AI 5) is the call's measured delivery from the core call status (D-38, delivered_kw, discharge positive); it is flagged COMM_LOST while that value is unmeasured or stale.
L2 LIMIT / BLOCK
The EMS sets a limit value (AO 16+t) and switches LIMIT or BLOCK per target (CROB 16+2t / 17+2t). A zone target applies to every bank in the zone, and the most restrictive level wins. MQTT user og_gridlink republishes the instructions on the existing <root>/scada/instruction/<bank_id> topic. og-engine and the guardian's own L2 port (G-15) therefore see them exactly as SCADA instructions. Since r3.4.3 the L2 levels are rebuilt across an og-engine restart by replaying the link's own trace (no migration). If that read fails, the link starts without levels and the EMS re-asserts them.
Security
Each utility has the following controls.
  • A peer IP allow-list (allowed_peers).
  • A client-certificate CN allow-list (allowed_peer_cns), required whenever it listens on a non-loopback address.
  • Its point list as the allow-list for controls: any other index is refused NOT_SUPPORTED.
  • A limit on concurrent associations.
Every inbound command except a heartbeat is traced before it takes effect (GRID_LINK_COMMAND, origin GRID_LINK, stream grid_link:<utility_id>). Refusals are traced as AUTHZ_DENY (GRID_LINK_DENY).
Heartbeat loss
The EMS pulses CROB 2. If no pulse arrives for heartbeat_timeout_s (30 s), the following apply.
  • New toll calls are refused (control status AUTOMATION_INHIBIT).
  • Cancels are still accepted.
  • A running call continues to its own end.
  • L2 levels stay as last received.
The state change is traced as GRID_LINK_STATE (HEALTHY / HEARTBEAT_LOST) and shown on the binary inputs LINK_HEALTHY and ALARM_HEARTBEAT_LOST. It raises no health alert. See the heartbeat playbook.
Configuration
[grid_link] in orchestrator.toml. The master switch and each utility's switch are false. The MQTT account is mqtt_username = "og_gridlink", with its password in mqtt_password_env. Entries for AUSTIN_ENERGY (port 20001), LCRA (20002) and RAYBURN (20003) ship disabled with placeholder peers from a documentation range. LCRA and RAYBURN have only suspended sample contracts (D-37). OG_GRID_LINK_CONFIG can point og-engine at an override file instead of the release config.
Loopback enablement (r3.4.3)
deploy/scripts/grid_link_enable_loopback.sh is a dry run unless given --apply. It creates a test PKI under /etc/opengrid/certs and the og_gridlink MQTT user. It writes /etc/opengrid/grid_link.toml, which enables AUSTIN_ENERGY on localhost port 20001 only, and adds an og-engine drop-in that sets OG_GRID_LINK_CONFIG. --test-call sends one short call through the AE simulator's grid link channel. --disable --apply rolls it back. See the wiring warning above.
Simulators
ogsim.scada can send its L2 instructions over the link (scada.yaml grid_link:, off unless set). The Austin Energy simulator ogsim.utility_aen can send its toll calls as a DNP3 master (utility_aen.yaml channel: grid_link, settings under channels.grid_link, localhost port 20001, test PKI). The shipped channel is customer_api.

Customer site ingest

Two topics carry customer site data, both QoS 0: <root>/site/<customer_id>/<site_id>/meter (customer_site_meter.schema.json) and <root>/corridor/<customer_id>/<corridor_id>/current (pipeline_corridor_current.schema.json). They are published by the customer's equipment or by the og_sim_customer simulator. opengrid.site_ingest validates each payload and checks that its customer and source ids match the topic, so one customer cannot write into another's loop. It keeps the newest reading per source in memory and flushes in batches on the engine's timer into og.customer_site_meter_reading and og.corridor_current_reading. The DATA_CENTER and PIPELINE_AC closed-loop controllers read these tables through the profile's feedback_signal_ref. The switch is [site_ingest].enabled, which ships false (on at go-live).

Outbound signed MQTT commands

Nothing reaches a hub unsigned. og-guardian signs command batches (<root>/cmd/<bank_id>/batch), leases (<root>/lease/<hub_id>, retained), calibration commands (cmd/cal) and firmware commands (cmd/fw). og-safestop signs stop ENGAGE events (<root>/stop/<scope>/<id>, retained). A stop RELEASE carries the guardian's signature after two-person approval.

Scheme
Ed25519 (RFC 8032) over the RFC 8785 JSON Canonicalization Scheme (JCS) bytes of the object without its signature and key_id fields. The signature is encoded base64url without padding, and key_id names the public key. Specified in interfaces/crypto.md.
Freshness
Every batch carries epoch, seq, issued_at and expires_at (lease-bounded, fleet.lease_ttl_s 30 s). Hubs verify the signature first, then freshness (K6, G-13). A hub whose lease expires holds its last signed setpoint.
Keys
Guardian: [guardian].key_path = /etc/opengrid/guardian_ed25519.key. Safe stop: [safestop].key_path = /etc/opengrid/safestop_ed25519.key. Trace anchors: /etc/opengrid/trace_anchor_ed25519.key. Since r3.4.1 each private key has its own group (og-guardian-key, og-safestop-key, og-anchor-key), and only the owning process is a member. og-api never holds a key.
Order
The decision pre-image is traced before signing (G-14, K10). The guardian publishes only after a PASS verdict. Since r3.4.3 the engine's hand-off to the guardian is bounded ([allocator].propose_timeout_s, default 2 s), so a stalled guardian holds the cycle instead of blocking it.

Firmware commands (cmd/fw)

<root>/cmd/fw/<hub_id>, QoS 1, not retained, schema firmware_command.schema.json. A campaign job asks the guardian's firmware hand-off (opengrid.firmware.guardian_flow). The hand-off reads every input itself, runs G-36 and signs only on PASS. The signed command is recorded in og.firmware_command and published. Refusals are holds: the engine re-requests after its defer interval. Catalogue refusals are the exception, because no amount of waiting fixes them. Campaigns are created and approved through the API (/og/api/firmware/campaigns).

ERCOT MMS adapter (submission disabled)

opengrid.integrations.ercot_mms is a QSE submission client for ERCOT MMS External Web Services. It covers energy and three-part offers and AS offers (BidSet create/cancel), DAM/RTM awards (AwardSet get) and verbal dispatch instructions (VDIs get and acknowledge). A submission is POSTed exactly once. Timeouts and 5xx responses are recorded as errors and never resent.

Submission is off twice over. The market backend defaults to backend = "none", and the factory refuses to build ercot_mms unless [integrations.market].enabled = true. Neither key is set in orchestrator.toml, so nothing is ever submitted to ERCOT. Since r3.4.2, og-feeds builds the same client read-only for AS deployment instructions when [feeds.ercot_as_poll] is enabled. In that mode it only reads instructions and answers them, with signing = "none" against the simulator. The Markets panel "Offer funnel (simulated)" counts only internal stages (made available, selected by the optimizer, committed, rejected); it has no submission or MMS count, and says that nothing is sent to ERCOT.

Customer API

opengrid.customer_api adds customer-scoped routes under /og/api/customer/.

  • me, contracts, obligations and obligations/{id}.
  • opportunities: priced admission; a rejection answers 409 with a reason_code.
  • invoices, invoices/{id}/dispute, disputes and requests.
  • obligations/{id}/cancel: direct only before selection, otherwise an operator-reviewed request.
  • obligations/{id}/renominate.

A customer is an Apache account mapped in [api.roles.customer]. Every read is scoped to its customer_id: another customer's object answers 404. A customer gets 403 on operator and viewer endpoints. Operators see requests at GET /og/api/customer-disputes and GET /og/api/customer-requests.

The same router set also serves the utility customer API (D-33, since r3.4.1) under /og/api/customer/v1/utility/. A utility account (role utility, mapped in [api.roles.utility] and listed in [api.utility_api].enabled_utilities, AUSTIN_ENERGY only) issues, cancels and follows its own toll calls. Those calls go through the same core call function as the operator and the grid link. The workstation's utility API docs describe it in full; see Utility customer API, how a utility call works and the utility call playbook. Its simulated caller is ogsim.utility_aen (unit og-sim-utility, channel: customer_api, installed by deploy/scripts/r343_utility_sim_install.sh). On hot days it issues an evening-peak call and reads the measured delivery. The /ogsim/ scenarios utility_call_normal, utility_call_overlap, utility_call_over_cap, utility_call_charge and utility_call_cancel_mid exercise it. LCRA and RAYBURN are listed in the simulator but disabled.

The routes are mounted only when [api.customer_api].enabled = true. The code default is false, but the shipped value has been true since r3.4.1 (D-33, owner request), so every customer route is live at r3.4.3. Apache admits only the accounts named on the /og/api/customer/ Require user line of deploy/apache/opengrid.conf: the og-cust-* accounts and og-util-aen. Bearer/OIDC stays off. See customer onboarding and APIs.

Utility customer API (r3.4.1, D-33)

A utility issues and follows its own toll calls under /og/api/customer/v1/utility/: GET me, GET obligations (its tolling obligations from today, America/Chicago, and today's window), POST calls, GET calls, GET calls/{id}, POST calls/{id}/cancel and, from r3.4.3, GET delivery-records and GET delivery-records/{call_id} (its own calls' measured delivery records, utility.read; another utility's record is 404). A customer reads its own contracts' records at /og/api/customer/delivery-records[/{call_id}] (docs/api/delivery.md). The Austin Energy EMS simulator (ogsim.utility_aen) calls it through Apache. Full reference: docs/api/utility-api.md.

Who
An Apache account listed in [api.roles.utility] gets the role utility and acts for the utility_id it maps to (og-util-aen = AUSTIN_ENERGY). Only utilities in [api.utility_api].enabled_utilities may use it: AUSTIN_ENERGY today. og-util-lcra and og-util-rayburn are mapped but not enabled (D-37). Any other identity, and a utility that is not enabled, gets 403. Apache admits the account only under /og/api/customer/, and og-api refuses it (403) on the operator and viewer endpoints.
Scope
Every read and call is limited to the caller's utility_id. Another utility's obligation or call answers 404 exactly like an unknown id, never 403. The attempt is traced as AUTHZ_DENY. The utility can read every call on its own toll, an operator's included, but from r3.4.3 it can cancel or shorten only the calls it issued: any other answers 403 R-CALL-NOT-ISSUER. From r3.4.3 every refused utility request, reads included, is traced as AUTHZ_DENY.
Calls
The body has a signed kw (negative: discharge only), duration_minutes, a required idempotency_key, and optional start_at and obligation_id (default: the toll whose window covers the start). The call goes through the same core as the Dispatch screen's utility call and the grid link, with origin UTILITY. The same checks apply: the 90-minute cap, the window, the committed kW, no overlap and a deployable state. The answer is 201 (200 for a replayed key), or the refusal's status with its reason_code. From r3.4.3 every timestamp needs a UTC offset (422 otherwise), and cancelling an ended call answers 409 R-CALL-ALREADY-ENDED (r3.4.2: R-CALL-CANNOT-EXTEND).
State
ACCEPTED before the start. While the call runs it is ACTIVE until its delivery is measured, then RAMPING or DELIVERING: measured discharge below, or at or above, [dispatch.calls].ramping_fraction (0.9) of the call's kW. COMPLETED after its end or a cancel, and REFUSED. From r3.4.3 (D-38), og-settle's delivery job measures each call in 30 s buckets, so the first measurement comes about a minute in. The status then carries delivered_kw/delivered_kwh, delivery_measured (true only once a measured value or a final verdict exists), delivery_state (UNMEASURED until then, then IN_PROGRESS, and PASS, PARTIAL or FAIL), delivery_reasons, meter_status and delivery_as_of. granted_kw/granted_kwh/granted_description are planned/granted values, never metered: "planned; removed in r3.5; use delivered_*". In r3.4.2 a running call is always ACTIVE, with delivery_measured: false and delivery_state: "UNMEASURED", and only the granted fields exist.
Limits
[dispatch.calls] allows at most 30 calls per rolling hour and 200 per rolling day per account. Accepted and refused calls count; replays do not. Over the limit: 429 R-CALL-RATE-LIMIT.
What operators see
ALR-UTILITY-CALL (info) on each accepted call and each cancel, and ALR-UTILITY-CALL-REFUSED (warning) on a refusal. The toll's row in the Dispatch screen's AS table reads deployed, "by UTILITY · og-util-aen"; its Delivery column shows the measured result, and clicking it opens the Measured delivery drawer (r3.4.3). Stop deploy ends the call. The trace stream is dispatch_call:og-util-aen.

The routes are mounted with the customer routes by [api.customer_api].enabled. When it is off, every utility path answers 404.
