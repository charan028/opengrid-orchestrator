Events, alerts and errors

What moves on the message bus, what raises an alert, which degraded modes exist, what each guardian veto code means, and how the processes behave when the broker, the database or the API is unavailable. Alerts are rows in og.alert, listed on /og/health and in the header bell; degraded modes are rows in og.degraded_mode_state and appear as the "Degraded:" banner.

Guardian checks G-01 to G-36

The guardian re-checks every proposed batch from its own reads and either signs it (PASS), vetoes it, or holds it (TIMEOUT). A veto carries the rule id and a reason code (core/reasons.py); bounds come from core/limits.py, the same functions the allocator uses, so the guardian never clips, it only passes or refuses. Missing or stale data fails closed. Codes marked "not implemented" are specified in docs/orchestrator/03-security/02-security-architecture.md but have no check in code at r3.4.

K7 escalation: CONSERVATIVE and safe-stop request

TIMEOUT is not VETO is not STOP. og-guardian counts vetoes per tick for every bank and for the zone containing it (guardian/escalation.py); only explicit invariant vetoes count, never timeouts or batches refused because a stop is engaged.

ParameterDefaultEffect
conservative_ratio5 %A tick with more than 5 % of the scope's commands vetoed is BAD: the scope goes CONSERVATIVE in og.scope_posture, ALR-SCOPE-CONSERVATIVE is raised and the escalation count rises by one.
stop_request_after3At a count of 3, ALR-SAFE-STOP-REQUESTED is raised with an unconfirmed safe-stop proposal for a person. Nothing here engages a stop; the operator uses the normal two-step flow.
clear_ratio_factor0.5A GOOD tick is at or under 2.5 %. A tick between 2.5 % and 5 % breaks the good streak and leaves the count alone.
clear_after_good_ticks3Three consecutive good ticks clear the scope back to NORMAL and clear both alerts. The count decays by one per good tick after that; it does not reset.
idle_clear_ticks30A CONSERVATIVE scope that sends no commands for 30 ticks also clears, with the same decay.

The engine honours CONSERVATIVE with reduced or zero new dispatch in that scope. On restart the guardian reconciles open escalation alerts against its state and resets scopes whose alerts it no longer tracks. See pb-veto-burst and pb-safe-stop.

Broker loss and reconnect

og-engine ingest (engine/mqtt_supervisor.py)
When the connection ends (MQTT error, keepalive timeout, stream closed) it reconnects with exponential backoff and jitter, 0.5 s doubling to a 30 s cap, one client at a time under the same client id, and resubscribes. After 30 s down ([mqtt].ingest_down_heartbeat_s) it stops writing its heartbeat, so health raises ALR-PROCESS-DOWN and HOLD_LOCAL_AUTONOMY. After 120 s ([mqtt].ingest_give_up_s) it exits with status 3 and systemd restarts it. Counter: og_engine_mqtt_reconnects_total.
og-guardian and og-safestop (platform/mqtt_session.py)
One long-lived session per process with a fixed client id; on disconnect the old client is closed and a new one opened after 1 s backoff doubling to 30 s. publish waits up to 5 s for a connection and then raises rather than dropping a message. The guardian holds signing while disconnected. Metrics: og_mqtt_reconnects_total, og_mqtt_connected.
og-safestop
Every (re)connect drains the stop outbox in order, so a stop accepted during an outage is published as soon as the broker is back (outbox).
Hubs
Retained lease and stop messages reach them on reconnect; without a fresh batch a hub holds its last signed setpoint until the lease (30 s) expires.

Client construction and schema validation are in platform/mqtt.py (build_client(), topic root, interfaces/mqtt schemas). Recovery steps: pb-broker-db.

Trace journal and anchoring

Every decision, command pre-image, verdict and operator action is written to the hash-chained og.trace (K10/K11). If the database write fails, the trace backend appends the entry to the local journal [trace].journal_path (/var/lib/opengrid/trace_journal.jsonl) and replays it later; a corrupt journal line is reported, never skipped. At r3.4 a manual-target confirm or cancel succeeds only once its row is in og.trace: if it reached only the journal, the API answers 503 "not recorded", and the engine never activates a target first seen more than 30 s after issue (it records a LATE_RECORD cancel).

og-settle's invariants hook anchors the chain head every 15 minutes (trace.anchor_interval_s, default 900): it signs the head hash with the anchor key, writes it to [trace].anchor_dir and the secondary copy anchor_secondary_dir, and records it in og.trace_anchor. While the anchor key is absent, anchors are published unsigned (logged). Failures raise ALR-ANCHOR-PUBLISH-FAILED or ALR-ANCHOR-SECONDARY-FAILED; scheduled verification raises ALR-TRACE-VERIFY-FAILED.

  1. Open /og/billing (Billing and audit), trace explorer.
  2. Set the class and From / To range, then Run chain verify.
  3. A pass shows the verified range; a fail shows the first broken link (stream and sequence). Do not edit rows; follow pb-security.

The same check is POST /og/api/trace/verify, open to viewers.

Safe-stop outbox

og-safestop never publishes a stop directly from the request. Each accepted ENGAGE or RELEASE is queued in og.stop_outbox (migration 0035, once per stop and action) and published from there at QoS 1, retained; an entry counts as published only when the broker acknowledges it. The outbox is drained on every (re)connect and on every tick as a backstop.

r3.4 behaviour (H5)What it means
Atomic recordThe og.stop_event row and its og.stop_outbox entry are written in one transaction (ENGAGE and relayed RELEASE). A failure can no longer leave a recorded stop with nothing to publish.
Redelivery repairA redelivered utility L2 instruction already acted on, whose ENGAGE has no outbox row, is re-signed under the same stop_id and queued (hubs de-duplicate by stop_id), never for a bank released since. A re-handed RELEASE already recorded is queued if missing.
Drain orderEvery ENGAGE before older RELEASEs, each oldest first.
Dead-letterAttempts count only permanent failures (a payload that can never be published); a broker outage stops the drain and never counts. At outbox_max_attempts (5) the entry is skipped, traced with reason SAFE_STOP_DEAD_LETTER, and ALR-STOP-PUBLISH-DEAD-LETTER (critical) is raised once, so one poison entry never blocks later stops.

A dead-lettered stop was not delivered to hubs. Treat it as a stop that did not happen: check the scope on /og/fleet and engage again if still needed (pb-safe-stop).
