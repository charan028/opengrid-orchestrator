Events, alerts and errors

What moves on the message bus, what raises an alert, which degraded modes exist, what each guardian veto code means, and how the processes behave when the broker, the database or the API is unavailable. Alerts are rows in og.alert, listed on /og/health and in the header bell; degraded modes are rows in og.degraded_mode_state and appear as the "Degraded:" banner.

MQTT topics

Broker: Mosquitto on localhost port 1883, plain TCP, loopback only. Every topic sits under [mqtt].topic_root (production og/v1; override OG_MQTT_ROOT), shown as <root>. Each process has its own MQTT user with an ACL limited to its rows; og-feeds (including the ERCOT AS poller, which uses HTTPS) and og-settle never touch MQTT. Every payload is validated against its schema in interfaces/mqtt/ before use.

r3.4.3 adds no new topic. Two new MQTT users reuse existing rows: og_gridlink (the D-34 grid link inside og-engine, publish-only on <root>/scada/instruction/#; exists only once the link is enabled, see grid link) and og_sim_utility (the Austin Energy EMS simulator ogsim.utility_aen, read-only on <root>/scenario/cmd; it places its calls over HTTPS through the utility API or over the DNP3 grid link, never over MQTT, see utility API).

Alert rules

Every rule writes through the same og.alert writer, raised once per condition key (never an alert storm). The health evaluator (inside og-settle) auto-clears only its own rules (HEALTH_OWNED_ALERT_RULES); an alert raised by another module stays open until that module clears it, or, where the table says "no automatic clear", until an operator acknowledges it on /og/health. Severities are critical, warning and info. info is a notice (firmware campaign progress, an accepted utility or AS call), never an action item. Before r3.4.3 one open info alert broke every reader of open alerts (the alert model accepted only warning and critical); r3.4.3 fixes that, so the Health page, the header bell and GET /og/api/alerts list info alerts normally.

CONSERVATIVE scope
A bank or zone in og.scope_posture CONSERVATIVE gets reduced or zero new dispatch; see K7 escalation.

The guardian signs nothing while its clock is out of limit (ALR-CLOCK-QUALITY).
Closed-loop HOLD
A DATA_CENTER or PIPELINE_AC loop that loses its customer signal holds the delivered level, then schedules.
Safe stop engaged
Batches for a stopped scope are refused (rule SAFE_STOP, not counted as a veto); see safe stop.
Guardian known unavailable (r3.4.3)
og-engine bounds its whole propose phase to [allocator].propose_timeout_s (2 s). Banks still pending at that point are cut off and the cycle moves on. Until the guardian writes a heartbeat newer than that timeout, the engine treats it as unavailable and holds instead of proposing (heartbeat read bounded by guardian_check_timeout_s, 0.5 s). Hubs keep their last signed command within its lease. Before r3.4.3 one database stall blocked a cycle for 25.6 s.
Grid link inhibited (D-34)
When the utility EMS's heartbeat is older than heartbeat_timeout_s (30 s), the link refuses new toll calls (INHIBITED). Cancels are still accepted, a running call continues to its own end, and L2 levels stay as last received. It is traced as GRID_LINK_STATE HEARTBEAT_LOST, logged at ERROR and shown to the EMS on the ALARM_HEARTBEAT_LOST point. No og.alert is raised. See pb-grid-link-heartbeat.
Regulated bank with no contract (D-37)
Banks in LZ_LCRA and LZ_RAYBN are UNAVAILABLE / REGULATED_NO_CONTRACT: nothing is dispatched there (R-BANK-UNAVAILABLE-REGULATED-NO-CONTRACT). The console shows "Regulated market – no contract". See pb-regulated-unavailable.
Uncorroborated price extreme (FR-ING-117, r3.4.1)
A real-time price outside the normal band (-250 to 5,000 $/MWh) but within the hard bounds is kept and flagged EXTREME_UNCORROBORATED, never clipped. While a series' latest price carries that flag, the forecast is NOT_FOR_FIRM. The same value in the next posting corroborates it. Values outside the hard bounds are quarantined.
Measured shortfall (D-38)
A live ALR-DELIVERY-SHORTFALL or ALR-DELIVERY-NONE flags the obligation AT_RISK. This is observation only: nothing is stopped (K7). See delivery verification.

Guardian checks G-01 to G-36

The guardian re-checks every proposed batch from its own reads and either signs it (PASS), vetoes it, or holds it (TIMEOUT). A veto carries the rule id and a reason code (core/reasons.py); bounds come from core/limits.py, the same functions the allocator uses, so the guardian never clips, it only passes or refuses. Missing or stale data fails closed. Codes marked "not implemented" are specified in docs/orchestrator/03-security/02-security-architecture.md but have no check in code at r3.4.3 (G-07, G-08, G-10, G-11, G-12, G-16, G-17, G-18); the other 29 codes, including G-01-ENERGY, are checked.

Sign-flip rule for unmapped topology (r3.4.1)

With [guardian.flow].fail_closed_missing_topology = true (false in the shipped config), a bank whose feeder (G-06/G-28/G-32) or substation (G-29) topology is missing gets a batch signed only when it is relief: the new net setpoint is no larger in magnitude than the previous one and on the same side of zero (or zero). A sign flip, from import to export or back, is never relief however small, because the unknown limit may bind in the other direction. The warning alert is raised either way.

Trucks away from their station: pb-trucks-away. A burst of vetoes is handled by pb-veto-burst; vetoes feed the K7 escalation.

K7 escalation: CONSERVATIVE and safe-stop request

TIMEOUT is not VETO is not STOP. og-guardian counts vetoes per tick for every bank and for the zone containing it (guardian/escalation.py); only explicit invariant vetoes count, never timeouts or batches refused because a stop is engaged.

Broker loss and reconnect

og-engine ingest (engine/mqtt_supervisor.py)
When the connection ends (MQTT error, keepalive timeout, stream closed) it reconnects with exponential backoff and jitter, 0.5 s doubling to a 30 s cap, one client at a time under the same client id, and resubscribes. After 30 s down ([mqtt].ingest_down_heartbeat_s) it stops writing its heartbeat, so health raises ALR-PROCESS-DOWN and HOLD_LOCAL_AUTONOMY. After 120 s ([mqtt].ingest_give_up_s) it exits with status 3 and systemd restarts it. Counter: og_engine_mqtt_reconnects_total.
og-guardian and og-safestop (platform/mqtt_session.py)
One long-lived session per process with a fixed client id; on disconnect the old client is closed and a new one opened after 1 s backoff doubling to 30 s. publish waits up to 5 s for a connection and then raises rather than dropping a message. The guardian holds signing while disconnected. Metrics: og_mqtt_reconnects_total, og_mqtt_connected.
og-safestop
Every (re)connect drains the stop outbox in order, so a stop accepted during an outage is published as soon as the broker is back (outbox). Its sessions (client="safestop" and "safestop-l2") are visible on its own /metrics at http://localhost:9106/metrics ([metrics].safestop_port, loopback, r3.4.1): og_mqtt_reconnects_total and og_mqtt_connected. The guardian's are on port 9103.
Grid link MQTT bridge (og-engine, D-34, only when enabled)
One connection as og_gridlink, reconnecting after 1 s doubling to 30 s. While it is down, L2 instructions are kept and re-sent on the link's next status tick; toll calls do not depend on it (they go straight to the calls core).
Utility simulator (og-sim-utility, r3.4.3)
Reads only <root>/scenario/cmd; a broker outage stops scenario triggers, not its calls.
Hubs
Retained lease and stop messages reach them on reconnect; without a fresh batch a hub holds its last signed setpoint until the lease (30 s) expires.

Client construction and schema validation are in platform/mqtt.py (build_client(), topic root, interfaces/mqtt schemas). Recovery steps: pb-broker-db.

Trace journal and anchoring

Every decision, command pre-image, verdict and operator action is written to the hash-chained og.trace (K10/K11). If the database write fails, the trace backend appends the entry to the local journal [trace].journal_path (/var/lib/opengrid/trace_journal.jsonl) and replays it later; a corrupt journal line is reported, never skipped. From r3.4.1 the journal write and the replay rewrite run off the event loop.

Quarantine (r3.4.1)

A journaled row that Postgres refuses for what it contains (a data or integrity error, for example a NUL character in a JSON string or a value outside a CHECK) can never succeed on retry. Replay moves it to <journal>.quarantine.jsonl (/var/lib/opengrid/trace_journal.jsonl.quarantine.jsonl, with the error) and continues with the rows behind it, so one bad row no longer stops replay for every process. Each quarantined row is reported once: a TRACE_QUARANTINED row on stream trace_quarantine (identifiers only, never the refused payload) and a critical ALR-TRACE-QUARANTINED. A database outage is not a content error: those rows stay in the journal and are retried. The quarantine file is the evidence; do not edit or delete it (pb-security).

Manual targets are DB-or-nothing

A manual target is traced on its own stream (manual_target:<user>) through a backend that never journals. A confirm or cancel succeeds only once its row is in og.trace. Otherwise the API answers 503 "not recorded" (nothing will ramp; retry), and no later replay can bring the row back. When the write failed and the follow-up lookup also failed, the API answers 503 "outcome unknown": check GET /og/api/fleet/manual-targets before retrying (API errors). The engine never activates a target first seen more than 30 s after issue (it records a LATE_RECORD cancel).

og-settle's invariants hook anchors the chain head every 15 minutes (trace.anchor_interval_s, default 900): it signs the head hash with the anchor key, writes it to [trace].anchor_dir and the secondary copy anchor_secondary_dir, and records it in og.trace_anchor. While the anchor key is absent, anchors are published unsigned (logged). Failures raise ALR-ANCHOR-PUBLISH-FAILED or ALR-ANCHOR-SECONDARY-FAILED; scheduled verification raises ALR-TRACE-VERIFY-FAILED.

  1. Open /og/billing (Billing and audit), trace explorer.
  2. Set the class and From / To range, then Run chain verify.
  3. A pass shows the verified range; a fail shows the first broken link (stream and sequence). Do not edit rows; follow pb-security.

The same check is POST /og/api/trace/verify, open to viewers.

Safe-stop outbox

og-safestop never publishes a stop directly from the request. Each accepted ENGAGE or RELEASE is queued in og.stop_outbox (migration 0035, once per stop and action) and published from there at QoS 1, retained; an entry counts as published only when the broker acknowledges it. The outbox is drained on every (re)connect and on every tick as a backstop.

Behaviour (r3.4 H5, updated r3.4.1)What it means
Atomic recordThe og.stop_event row and its og.stop_outbox entry are written in one transaction (ENGAGE and relayed RELEASE). A failure can no longer leave a recorded stop with nothing to publish.
Redelivery repairA redelivered utility L2 instruction already acted on, whose ENGAGE has no outbox row, is re-signed under the same stop_id and queued (hubs de-duplicate by stop_id), never for a bank released since. A re-handed RELEASE already recorded is queued if missing.
Drain order (corrected in r3.4.1)Within one scope (fleet, a zone or a bank), entries go out strictly in acceptance order (seq): a hub drops a RELEASE older than the newest ENGAGE on its scope, so a newer ENGAGE must never overtake an older RELEASE of the same scope, or the bank would stay stopped. ENGAGE goes first only across scopes: of the entries at the head of each scope, the oldest ENGAGE goes before any RELEASE, so a stop never waits behind another scope's release. (r3.4 sent every ENGAGE before every older RELEASE regardless of scope.) Since r3.4.3 each drain reads the oldest 100 live entries plus every entry of each scope with a queued ENGAGE, wherever it sits, so a stop never waits behind a long backlog; its scope's older entries still come with it, in order.
Superseded release (r3.4.3)A guardian-signed RELEASE whose signed issued_at is older than the newest ENGAGE on its scope is refused: og-safestop cannot re-stamp it and the hubs would drop it. Nothing is published or recorded in og.stop_event, so the hubs and the database agree that the scope is stopped. A SAFE_STOP trace (reason SAFE_STOP_RELEASE_SUPERSEDED, payload superseded_signature) marks it, ALR-STOP-RELEASE-SUPERSEDED (warning) is raised once while open, and the guardian's re-hand query skips it. The operators re-issue the two-person release, which the guardian signs after the ENGAGE and og-safestop relays normally.
In-request drainRight after a stop is accepted and queued (API or utility L2 intake), og-safestop drains the outbox, serialised with the tick and reconnect drains, so a stop does not wait for the next tick. That drain never fails the request: the stop is already recorded and queued, and the next drain publishes it.
Dead-letterAttempts count only permanent failures (a payload that can never be published); a broker outage stops the drain and never counts. A permanent failure holds back only its own scope's later RELEASEs, never an ENGAGE (r3.4.3: an ENGAGE published ahead of an older RELEASE wins at the hubs, the safe side). At outbox_max_attempts (5) the entry is skipped, traced with reason SAFE_STOP_DEAD_LETTER, and ALR-STOP-PUBLISH-DEAD-LETTER (critical) is raised. Every drain re-raises it idempotently for every dead-lettered entry (one open alert per entry, traced when newly raised), so an entry dead-lettered by a crash or found at the cap after an upgrade is never silent. Since r3.4.3 a dead-lettered ENGAGE is retried on every drain after the live queue and traced DEAD_LETTER_PUBLISHED once it goes out; a dead-lettered RELEASE is only alerted. Other scopes carry on.

A dead-lettered stop was not delivered to hubs. Treat it as a stop that did not happen: check the scope on /og/fleet and engage again if still needed (pb-safe-stop).

Delivery verification events and alerts (D-38, r3.4.3)

og-settle's delivery job (opengrid.delivery, [delivery]) measures every discharge call from telemetry, never from grants: utility toll calls, ERCOT AS deployments and operator manual discharge targets. It is observation only (K7): it never changes dispatch, and a measured shortfall never stops a firm obligation. How the measurement works is in delivery verification.

Cadence
Every interval_s (15 s), in bucket_s (30 s) buckets, after waiting telemetry_lag_s (30 s) for late telemetry. A call is followed until it has a final record, up to lookback_s (1 h) after it ended. One call's failure is logged and never stops the others.
Record
One row per call in og.delivery_record (migration 0050), updated as buckets arrive. The final record carries the result: PASS, PARTIAL or FAIL (IN_PROGRESS until then), the reasons (RAMP_TOO_SLOW, SUSTAIN_BELOW_TARGET, NO_DELIVERY, VETOED, STOPPED, DATA_STALE, ENERGY_SHORT) and the meter check (CORROBORATED, UNCORROBORATED, NO_METER, METER_STALE).
Trace
Each final record is traced once on stream delivery (DELIVERY_RECORD / DELIVERY_VERIFICATION, reason codes R-DELIVERY-<result>, the reasons and R-METER-<status>). Each alert it raises is also traced (ALERT / DELIVERY_ALERT).
Alerts
ALR-DELIVERY-RAMP-LATE, ALR-DELIVERY-SHORTFALL and ALR-DELIVERY-NONE are live alerts while the call runs; the job clears them when the condition ends or the call ends. ALR-DELIVERY-METER-MISMATCH is raised on a final record whose meter check is UNCORROBORATED and stays open until an operator clears it. All are critical and owned by the job; the health evaluator never clears them (alert rules).
AT_RISK
While a live SHORTFALL or NONE alert stands, the obligation is flagged AT_RISK with R-DELIVERY-MEASURED-SHORTFALL through the single AT_RISK writer; on recovery or at call end the job clears only the flag it set (R-DELIVERY-RECOVERED). The engine's own AT_RISK causes and its mid-window SHORTFALL escalation are unchanged.
Where to see it
On /og/dispatch, the Delivery column of "AS awards & deployment" for each deployed toll or AS call, and the Measured delivery drawer it opens (see Dispatch). Through the API: GET /og/api/delivery/records (filters: service type, contract, call kind, result, utility, call ids, date range), GET /og/api/delivery/records/{call_id} (with the per-bucket series) and GET /og/api/delivery/summary, all viewer. Call status for the utility API and the grid link now reports measured delivered_kw, delivery_state and meter_status. The call status keeps the deprecated granted_kw/granted_kwh/granted_description for one release (removed in r3.5), and delivery_measured is true only once a measured delivered kW or a final verdict exists. A utility reads its own records at /og/api/customer/v1/utility/delivery-records[/{call_id}], a customer at /og/api/customer/delivery-records[/{call_id}]. The utility API side is described in utility API.

What to do when one of these alerts opens: pb-delivery-alert.
