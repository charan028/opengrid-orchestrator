## 1. Bottom line

1. **Not ready to build.** The set is broad and careful, but it contradicts itself on the four mechanisms that make the system safe and scalable: who owns a multi-partition arbitration, how commands are signed and persisted, how the audit chain is built, and how the message bus is laid out.
2. As 01 specifies it, every command passes through one single-replica Python guardian and one Postgres row lock, and 03 counts a guardian timeout as a veto that escalates to a safe stop. A performance hiccup becomes a fleet stop, and a 10,000-hub stop cannot be signed within one control cycle.
3. **The node does not fit** once the other documents' own component sizes are used: ≈ 11,775–13,910 MiB (≈ 11.5–13.6 GiB) of requests against 10,496 MiB. The control path is not protected from the kernel OOM killer. Running the load generator on the same node would make every performance number unverifiable.
4. **The NATS design exists in three incompatible versions.** With the caps and DiscardNew of 05 and 06, the command, audit and call streams fill in minutes to days and then halt dispatch.
5. **The schedule is not credible.** It builds ≈ 16 services, ≈ 25–30 platform components, four SCADA stacks and ≈ 1,185 test cases in ≈ 3 weeks before a 10-20 gate. Freeze a demo-critical path now, and decide partitioning, guardian HA, the audit chain and the streams in ADRs before any code.
